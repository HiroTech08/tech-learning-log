# Goの `map` と各言語のキー・バリュー型

Goの `map` は **ハッシュテーブルベースのキー・バリュー構造** である。本ドキュメントでは各言語の対応型を、順序保証・存在確認イディオム・木構造ベースの代替型といった「性質や仕様の違い」を軸に整理する。

---

## 1. 対応型一覧

| 言語 | 主な型 | 内部実装 | 順序 | ゼロ値/初期化 |
|------|--------|----------|------|---------------|
| Go | `map[K]V` | ハッシュテーブル | 順序なし（イテレーション順をランダム化） | `nil`（要 `make`） |
| Rust | `HashMap<K, V>` | ハッシュテーブル | 順序なし | `HashMap::new()` |
| Rust | `BTreeMap<K, V>` | B木 | キーでソート済み | `BTreeMap::new()` |
| Python | `dict` | ハッシュテーブル | 挿入順を保持（3.7+で仕様化） | `{}` / `dict()` |
| TypeScript/JS | `Map<K, V>` | ハッシュテーブル | 挿入順を保持 | `new Map()` |
| TypeScript/JS | `Record<K, V>` / `{}` | オブジェクト | 概ね挿入順（数値キー除く） | `{}` |
| C++ | `std::unordered_map` | ハッシュテーブル | 順序なし | デフォルト構築 |
| C++ | `std::map` | 赤黒木 | キーでソート済み | デフォルト構築 |
| Java | `HashMap<K, V>` | ハッシュテーブル | 順序なし | `new HashMap<>()` |
| Java | `TreeMap<K, V>` | 赤黒木 | キーでソート済み | `new TreeMap<>()` |
| Java | `LinkedHashMap<K, V>` | ハッシュテーブル+双方向リスト | 挿入順を保持 | `new LinkedHashMap<>()` |

---

## 2. 最大の違い：順序の扱い

連想配列を他言語へ移植するときに最も挙動が変わるのが **イテレーション順** である。

- **順序なし（ハッシュ順）**：`Go map` / `Rust HashMap` / `C++ unordered_map` / `Java HashMap`
- **挿入順を保持**：`Python dict` / `JS Map` / `Java LinkedHashMap`
- **キーでソート済み（木構造）**：`Rust BTreeMap` / `C++ map` / `Java TreeMap`

### 「ハッシュ順」とは
ハッシュテーブルの内部構造によって決まる、**キーが格納された物理的な並び順**を指す。ハッシュテーブルはキーをハッシュ関数にかけて得たハッシュ値をもとに、内部配列のどの位置（バケット）へ値を置くかを決める。

```
キー "banana" → ハッシュ関数 → 3892... → バケット 5 番
キー "apple"  → ハッシュ関数 → 1047... → バケット 2 番
キー "cherry" → ハッシュ関数 → 8821... → バケット 9 番
```

イテレーションは **挿入順でもソート順（abc順）でもなく、このバケットの並び順** で行われる。上の例なら `apple(2) → banana(5) → cherry(9)` となり、人間が意図した順序とは無関係になる。これが「ハッシュ順」であり、本ドキュメントでは **順序なし** の言い換えとして使っている。

なお一般的なハッシュテーブルでは「ハッシュ順 = 実装が同じなら毎回同じ順」になる（ランダムなのではなく、たまたまソート順と一致しないだけ）。後述のとおり Go だけはこの順序を意図的にランダム化している点が特殊である。

### Goの特殊事情
Goの `map` はイテレーション順が **意図的にランダム化** されている。これは順序依存のバグを生まないための設計判断であり、「ハッシュ順だが毎回同じ順」ではなく「実行ごとに変わる」点に注意する。

```go
for k, v := range m {
    // 実行のたびに順序が変わる。順序に依存してはいけない
}
```

### 感覚の近さ
- Go から Rust への移植 → `HashMap` は同じく順序なしで感覚が近い
- Go から Python / JS への移植 → 相手は挿入順を保持するため、**Go側でランダムだった順序が、移植先では安定して見える** ことに注意（順序依存バグが顕在化しにくい代わりに、順序を仕様と誤認しやすい）

### 順序が必要になったら
ソート順が欲しい場面では木構造ベースの型へ切り替える。

| 元の型 | ソート版 |
|--------|----------|
| `Rust HashMap` | `BTreeMap` |
| `C++ unordered_map` | `std::map` |
| `Java HashMap` | `TreeMap` |
| `Go map` | 標準にソート版はない。キーを別途 `sort` する |

```go
// Goでキー順に処理したい場合
keys := make([]K, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Slice(keys, func(i, j int) bool { return keys[i] < keys[j] })
for _, k := range keys {
    use(m[k])
}
```

## 3. 存在確認のイディオム

Goの `v, ok := m[k]` に相当する書き方は言語ごとに異なる。思想が最も近いのは **Rustの `Option` 型**。

| 言語 | 書き方 | 戻り値/挙動 |
|------|--------|-------------|
| Go | `v, ok := m[k]` | `ok` が `bool`。キーがなければ `v` はゼロ値 |
| Rust | `m.get(&k)` | `Option<&V>`（`Some` / `None`） |
| Python | `m.get(k, default)` / `k in m` | `get` は無ければ `None`（または既定値） |
| TS/JS | `m.has(k)` / `m.get(k)` | `get` は無ければ `undefined` |
| C++ | `m.find(k) != m.end()` | イテレータで判定 |
| Java | `m.containsKey(k)` / `m.get(k)` | `get` は無ければ `null` |

### 落とし穴：「ゼロ値」と「存在しない」の区別
Goでは `m[k]` がキー欠如時にゼロ値（`int` なら `0`、`string` なら `""`）を返すため、**値がゼロなのかキーが無いのかを `ok` なしには区別できない**。同じ問題が以下にもある。

- Python：値が `None` の場合と未登録の場合 → `in` で明示確認
- JS：値が `undefined` の場合と未登録の場合 → `has()` で明示確認

Rustの `Option<&V>` はこの曖昧さが型で排除されているため、移植時の安全性が高い。

## 4. JavaScript / TypeScript：`Map` vs オブジェクト

Goの `map` から来ると `Record<string, V>`（≒オブジェクト）を選びがちだが、用途次第で `Map` が正解になる。

| 観点 | `Record` / `{}` | `Map` |
|------|-----------------|-------|
| キーの型 | 文字列 / Symbol のみ | 任意の型（オブジェクトも可） |
| サイズ取得 | `Object.keys(o).length` | `m.size` |
| 反復 | `for...in` / `Object.entries` | `for...of` / `m.forEach` |
| 順序 | 数値キーが昇順に繰り上がる癖あり | 挿入順を厳密に保持 |
| プロトタイプ汚染 | リスクあり（`__proto__` 等） | なし |
| 頻繁な追加・削除 | 不向き | 最適化されている |

### 使い分けの目安
- **`Record`**：固定的な構造、JSONとの相互変換、キーが既知の文字列セット
- **`Map`**：任意型キー、サイズを頻繁に参照、追加削除が多い、順序を厳密に扱う

---

## 5. 移植チェックリスト

GoのCLIツールを他言語へ移植する際に確認すべき点。

- [ ] **順序依存**：イテレーション順に依存したロジックがないか。あるなら移植先で挙動が変わる
- [ ] **ゼロ値依存**：キー欠如時のゼロ値前提のコードがないか（特に数値・文字列）
- [ ] **存在確認**：`v, ok` パターンを移植先の `Option` / `has` / `containsKey` に正しく置換したか
- [ ] **ソート要件**：キー順出力が必要なら木構造型（`BTreeMap` 等）を選ぶ
- [ ] **キーの型**：JSへ移植する場合、非文字列キーなら `Record` ではなく `Map` を使う

---

## 付録：計算量の目安

| 操作 | ハッシュテーブル系 | 木構造系（BTreeMap / std::map / TreeMap） |
|------|-------------------|-------------------------------------------|
| 挿入 | 平均 O(1) | O(log n) |
| 検索 | 平均 O(1) | O(log n) |
| 削除 | 平均 O(1) | O(log n) |
| キー順走査 | 別途ソート O(n log n) | O(n)（既にソート済み） |

ハッシュ系は最悪 O(n)（衝突多発時）になり得るが、実用上は平均 O(1) として扱う。順序付き走査が頻繁なら、木構造系の O(log n) を受け入れる価値がある。
